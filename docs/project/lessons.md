# 纠错与反思

`docs/project/lessons.md` 记录用户对 AI 的纠正，以及 AI 在工作中发现并修正的错误。每次开工必须先完整阅读本文件。

## 记录规则

- 每次真实纠正后立即新增一条，不积压、不凭空编造。
- 固定格式：**现象 → 原因 → 防止规则**。
- “防止规则”必须具体、可执行，并在后续工作中持续遵守。
- 如果纠正形成长期项目规则，同时更新 `AGENTS.md`。

## 记录

### 2026-08-23 · 访谈问题过于抽象

现象 → AI 用“输出结构固定到什么程度”“不适用环节是否保留”等抽象措辞提问，用户无法直观判断并要求举例。

原因 → AI 只描述了格式概念，没有用同一道具体考研数学题展示不同输出效果。

防止规则 → 此后的需求访谈只要涉及抽象格式、交互或风格差异，就先给出简短、具体、可对比的实例，再用一个明确问题让用户判断。

### 2026-08-23 · 根目录重命名后补丁路径失效

现象 → 项目根目录从 `KaoYan` 重命名为 `DaXueShenMai` 后，仍绑定旧工作区路径的内置补丁调用无法读取当时位于根目录的进度文档（现为 `docs/project/progress.md`）。

原因 → 根目录名称改变了，但当前任务的补丁工作区没有同步刷新。

防止规则 → 以后重命名项目根目录前先完成所有待写文档；重命名后先在新目录验证读取与补丁编辑能力，再继续修改文件。

### 2026-08-23 · 不得猜测阅卷得分点

现象 → AI 在确认判题范围时提出了“按考研阅卷方式估算得分并指出得分点”，用户指出这类内容很容易引发幻觉。

原因 → 没有具体、权威的评分细则时，模型无法可靠还原真实阅卷规则，估分会把推测包装成事实。

防止规则 → `dxsm-math` 只依据题干、数学定理和可检查的推导判断步骤与结果；不估分、不猜得分点。任何信息不足或无法可靠验证的内容都应明确说明并向用户补充询问，禁止无依据生成。

### 2026-08-23 · 主推导不使用引用块

现象 → AI 用 Markdown 引用符号 `>` 包裹完整的逐步数学推导，用户认为可读性不高。

原因 → 引用块会增加视觉缩进并呈现为附注样式，不适合承载公式密集的主线推导。

防止规则 → 数学解题主线使用编号小标题、普通正文和居中的独立展示公式；说明文字保持左对齐。引用块只用于真正引用用户原话或题干片段，不用于包裹完整解答。

### 2026-08-23 · 区分题干缺失与条件不足型考点

现象 → AI 在举例时把“输入不清晰或题干残缺”和“题目完整但现有条件无法推出目标结论”混为同一种情况。

原因 → AI 只关注了信息不足，没有先判断这种不足是否正是题目要求考生识别的数学结论。

防止规则 → 先判断题目语义是否完整：识别结果有歧义或疑似缺字时向用户追问；题目完整且考查条件能否推出结论时，直接依据充分性分析作答，并在需要时给出反例，不擅自要求补充条件。

### 2026-08-23 · 不引入无关的 API Key 概念

现象 → AI 在讨论 Skill 测试时直接提到 API Key、费用和自动调用模型，让用户误以为项目运行需要密钥。

原因 → AI 没有先说明 Skill 由 Codex 或安装后的 Agent 直接执行，把可选的云端自动化测试方案与项目本身混在了一起。

防止规则 → 先明确 `dxsm-math` 本身不需要 API Key，也不保存密钥。只有用户明确要求独立的云端模型测试脚本时才讨论 API 凭据；v1 测试由当前 Codex 会话或安装后的 Agent 执行。

### 2026-08-23 · 错误地将 AGENTS.md 降级为历史文件

现象 → AI 在压缩上下文胶囊中错误降低了 `AGENTS.md` 的规范地位，与用户要求其作为持续维护的仓库执行规范相冲突。

原因 → AI 把一次关于旧指令适用性的上下文判断错误扩大成了对整个文件地位的永久否定，没有回到 `AGENTS.md` 本身核对“活文档”定位，也没有区分“某条旧指令被替换”和“整份执行规范失效”。

防止规则 → 任何单条规则被用户替换时，只修改受影响条款，不得推断整份 `AGENTS.md` 失效。每次开工必须先读 `docs/project/lessons.md` 和 `AGENTS.md`；生成上下文胶囊、权威顺序或交接说明时，必须明确 `AGENTS.md` 是持续生效的执行规范，并搜索全仓库确认没有把它排除在规范来源之外。

### 2026-08-24 · rg 默认模式不支持回顾断言

现象 → AI 在迁移文档后的路径审计中直接向 `rg` 传入回顾断言，命令因默认正则引擎不支持 lookbehind 而失败。

原因 → AI 没有先判断表达式是否需要 PCRE2，也没有优先使用足以完成任务的简单兼容搜索。

防止规则 → 使用 `rg` 设计审计命令时优先采用默认引擎支持的简单表达式；确实需要 lookaround 时显式加入 `--pcre2`。命令失败后先确认没有产生写入，再以更简单的兼容表达式重跑。

### 2026-08-24 · 控制字符和双重转义导致补丁拒绝

现象 → AI 第一次直接修补含原始 CR 的损坏 LaTeX，补丁 hunk 被控制字符拆行；第二次改用 `String.raw` 时又把 Markdown 反引号前的转义斜杠保留进补丁上下文。两次补丁均被完整拒绝，没有产生部分写入。

原因 → AI 把控制字符恢复、LaTeX 转义和 Markdown 上下文混在同一个大补丁中，没有先规范化不可见字符，也没有按字符串构造方式核对补丁的实际字节内容。

防止规则 → 含 CR、Tab 或多层反斜杠的文件先只读定位；确认是转义损坏后，先机械恢复字面反斜杠。普通 Markdown 与 LaTeX 分开提交小补丁；使用 `String.raw` 时不得沿用普通模板字符串的反引号转义写法。每次补丁失败后必须确认没有部分写入再继续。

### 2026-08-24 · apply_patch 失败仍可能留下部分写入

现象 → 一个同时修改多个文件和多个 hunk 的补丁报告失败后，`.gitignore` 没有创建，但排在失败点之前的 `AGENTS.md` 禁止项已经写入。AI 最初只检查首个目标文件，错误地判断整个补丁没有部分写入。

原因 → AI 把补丁失败误当成事务性回滚，没有逐一检查补丁涉及的所有文件和所有先行 hunk。

防止规则 → 不假设 `apply_patch` 失败具有原子性。跨文件修改优先拆成单文件小补丁；任何失败后必须检查该补丁涉及的每个文件、Git diff 和目标文本，再决定重试内容，避免重复写入或漏记状态。

### 2026-08-25 · YAML 流式数组中的矩阵文本必须引用

现象 → `synthetic-cases.yaml` 把 `最终结果为[[1,n],[0,1]]` 作为未加引号的流式数组元素，Ruby YAML 解析器把内部方括号当成嵌套语法，导致整份合成测试文件无法解析。

原因 → 创建测试资产时只核对了用例数量和文本内容，没有在阶段结束前使用真实 YAML 解析器加载文件；同时忽略了流式数组中的方括号、花括号、冒号等字符会改变 YAML 语法。

防止规则 → 新建或修改 YAML 后必须立即用可用的标准解析器完整加载，再统计与校验字段。流式数组或映射中的矩阵、区间、公式等含结构符号文本一律加引号；未通过解析前不得把测试资产定义阶段记为完成。

### 2026-08-25 · 渐进式披露不能形成引用深链

现象 → `SKILL.md` 已直接链接三份参考文件，但 `syllabus-scope.md` 又链接 `topic-taxonomy.md`，形成了 `SKILL.md → reference → reference` 的二级导航链，不符合本项目只使用一层引用的验收约束。

原因 → 编写参考文件时沿用了普通文档之间互相导航的习惯，只检查链接是否存在，没有同时检查从 Skill 入口出发的引用深度。

防止规则 → Skill 资源校验必须同时检查“目标存在”和“最大引用深度”。本项目的参考文件全部由 `SKILL.md` 直接路由，reference 内不得再链接其他内部 Markdown；只有外部官方来源链接可以保留。

### 2026-08-25 · 静态断言不得收窄语义规范

现象 → 临时 README 审计脚本额外要求正文逐字包含 `dxsm-english` 与 `dxsm-408`，因而报告失败；实际规范只要求说明三个独立 Skill 的规划和当前状态，README 已通过统一 `dxsm-` 前缀及“数学、英语与 408，v1 仅提供 `dxsm-math`”完整表达该语义。

原因 → 编写机械断言时把便于搜索的具体字符串误当成规范原文，没有先区分“必须表达的语义”和“必须逐字出现的文本”。

防止规则 → 静态检查只对规范明确固定的名称、路径、命令和字段做精确匹配；对说明性要求先人工审查语义，再用多个必要证据验证，不得为了让临时断言通过而改写本来合格的产品内容。

### 2026-08-25 · 旧试卷题号必须按原卷结构核验

现象 → 固定回归索引用阿拉伯数字表示 1987 年旧卷的罗马数字大题，语义不够明确；数一第八、九、十大题的起始页还误记为第 3 页，实际位于第 4 页并有跨页内容。

原因 → 选题阶段只做了部分页面视觉抽查和总量分配，没有逐条建立“原卷大题/小题 → PDF 页码 → 题型”的可复核映射，并混用了现代连续题号与旧卷大题号两套表达。

防止规则 → 真题索引中的年份、卷别、页码、题号和题型必须在创建时逐条对照原页验证。对旧卷分大题编号的情况，使用不歧义的原卷定位字符串，不得擅自套用现代连续题号；定位与题型未核验前不得计入分配覆盖或开始答案复核。

### 2026-08-25 · PDF 空文本页不能替代视觉核对

现象 → `pdftotext` 对数二 1987 第 4 页和数三第 4—5 页只返回换页符，AI 一度误判这些页没有题目并修改索引；实际渲染后可清晰看到数二第十题、数三第三、九、十一题，原题型和页码大部分正确。

原因 → AI 在已有“优先视觉审查”的 PDF 规则下，仍把缺失的文本层当成页面为空的证据，没有先区分扫描图像、字体映射失败与真正空页。

防止规则 → PDF 文本提取为空、乱码或与答案目录冲突时，必须先渲染原页视觉核对，再修改定位或题型。文本层只用于检索和辅助抄录，不能否定可见页面内容；任何基于空提取做出的修补都要在视觉确认后才能保留。

### 2026-08-25 · 未见题封存不等于可以使用泛化题型标签

现象 → 未见题索引在封存阶段为数二、数三多道题写入了“可导与连续”“矩阵与向量”“综合计算”等宽泛题型，其中数一 2025 第 10 题还误标为置信区间；解封并核验原页后，实际分别涉及单侧均值检验、无穷小关系、二次型惯性指数、斜渐近线、由极限确定导数、方程组可解性、反常积分参数和泊松赔付模型。

原因 → 选取未见题时为了避免提前求解，只按页码和粗略版块做了占位分类，把“不读取答案、不用于调优”错误扩大成了“不必逐条视觉核验题目所属知识点”。

防止规则 → 封存未见题时可以不求解、不读答案，但仍必须逐条视觉核验年份、题号、页码和客观题型；看不清时写 `unknown`，不得用宽泛标签猜填。解封后若题型细化与索引不一致，必须在答案复核前先修正索引，并重新用标准解析器校验。

### 2026-08-25 · 公共 Release Notes 不自动收录内部工具限制

现象 → 发布说明预览加入了 quick validator、PyYAML 和 `skills-ref` 的环境限制，用户明确要求删除该段。

原因 → AI 把仓库内部验收报告需要保留的透明度信息直接扩展到了面向使用者的公共发布摘要，没有区分两类文档的受众与目的。

防止规则 → Release Notes 只使用用户最终批准的发布内容；内部校验工具限制继续保留在测试报告和项目进度中，但除非会影响用户安装或使用，或者用户要求披露，不自动加入公共 Release Notes。

### 2026-08-29 · 上下文胶囊不得固化短期 Git 状态

现象 → 上下文胶囊仍要求恢复者保留“当前未跟踪”的 `README.md`、`LICENSE`、`skills/` 和 `evals/`，但仓库实际已经提交这些文件且工作区干净；若照抄这条历史状态，恢复判断会失真。

原因 → 胶囊在发布准备阶段记录了当时的短期 Git 状态，后续阶段变化时没有把这类瞬时事实改成以实时检查为准的恢复规则。

防止规则 → 上下文胶囊只保留经阶段同步确认的持久事实；分支 ahead/behind、已修改文件、未跟踪文件和正在运行的步骤必须写入 `docs/project/progress.md` 的当前检查点，并在恢复时用 Git 和实际产物重新核对。任何压缩、交接或阶段变化前都要删除或更新胶囊中的过时瞬时状态，不得让历史描述覆盖实时证据。

### 2026-09-01 · “只做作文与翻译”不等于禁止生成范文

现象 → 在 `dxsm-english` 需求访谈中，AI 把用户所说“只提供批改作文和批改翻译、不要客观题”擅自收窄为“必须先有用户作答，不允许根据作文题目生成范文”；用户纠正确认可以生成范文，并要求范文严格依据评分标准达到尽可能高的质量。

原因 → AI 把产品支持的题型边界与具体交互模式混为一谈，从“只覆盖主观题”错误推出“只允许纠错、不允许示范作答”，没有先单独确认作文范文和直接翻译的能力边界。

防止规则 → 需求中的“只做某类题”只限定题型范围，不自动限定为批改、讲解或生成中的某一种模式。设计新 Skill 时必须分别确认每种题型是否支持用户作答批改、从零示范、最小修订和优化版本；未经用户确认不得用一种交互模式替代整个能力范围。

### 2026-09-01 · shell 搜索表达式中的反引号必须避免双引号解析

现象 → 最终规范冲突审计把含反引号的搜索表达式放进双引号 shell 参数，zsh 将反引号当作命令替换边界并报 `unmatched "`，该只读搜索没有执行，也没有产生写入。

原因 → 组装 `rg` 命令时只关注正则内容，没有先检查反引号在 shell 双引号中的特殊含义。

防止规则 → shell 搜索模式含 Markdown 反引号、美元符号或命令替换字符时，优先使用不含这些字符的等价简单模式；确需保留时用安全的单引号参数，并在执行前检查引号成对。失败后先确认无写入，再重跑兼容命令。

### 2026-09-11 · 输出顺序与运行入口重复造成约束漂移

现象 → 审计发现输出规范最大结构将选项分析列在最终答案之后，但同文件 OUT-CH-001 和 Skill 要求之前；同题追问的局部补充规则只在分层规范，Skill 入口未明确路由；RUN-R8-001 泛称判题需过程，与 P-CORRECT-1 允许仅判断最终结果表述不一致。AGENTS 与胶囊还多次复制检查点流程和瞬时状态。

原因 → 同一行为在多个入口分别维护，列表、明确条款和运行指令缺少交叉核对；历史恢复材料逐步变成重复规范。

防止规则 → 维护流程只在 workflow 保存细则；产品修订同时核对编号条款、输出顺序与 Skill 分支。胶囊保存持久背景并指向实时检查点；历史测试保持原日期，不冒充当前重构后的运行证据。

### 2026-09-11 · 精简指标必须先测量再报告

现象 → 中途说明把 AGENTS.md 原行数报为 304；随后从 Git HEAD 实测是 266 行，已立即向用户更正。

原因 → 口头更新使用了未核验的行数估计。

防止规则 → 文件行数、字符数及精简比例必须先从基线与当前文件计算；不用行数或字符数代替真实 token、延迟或模型质量测量。

本轮工具纠错补充：一次中文内联 Python 输入在解析阶段报非 UTF-8 错误，逐文件复查确认没有写入后改用单文件补丁。输入编码错误不能假定已经执行了前置修改；原因不明时不猜测具体编码来源，先验证状态再重试。

### 2026-09-11 · 不触发完整流程不等于禁止提供范围外服务

现象 → 独立前向验证 SYN-TRG-N-02 实际生成六个月复习计划，违反既有 GOV-020；只写“不进入解题流程”未能可靠表达服务边界。

原因 → 指令把纯定义的普通简答与备考管理的服务排除放在同一句，模型将两类负向触发都理解为可转普通聊天完成。

防止规则 → 区分“不套完整流程但可简答”与“不提供此服务只说明范围”；边界测试保存实际输出，发现阻断后先测失败/同类场景，再跑全部固定回归，不只改关键词便宣布通过。

### 2026-09-11 · 来源核实用例不能暗含未请求的求值任务

现象 → SYN-REL-03 只问积分题的年份题号来源，测试却用无条件“数学结果正确”断言要求附带求值；实际回答正确披露来源未知，没有解用户未要求的积分。

原因 → 把“可独立算出”的可选行为写成无条件验收，混淆来源核实与明确求值的任务范围。

防止规则 → 来源专用请求只强制核实边界，附带数学结果则检查正确性；另用同时要求求值与核实来源的请求测试独立可解部分。保留初次实际输出与断言调整理由，不把未观察到的行为记为通过。

### 2026-09-11 · 答案册隐含正参数不能代替题干条件

现象 → 本轮固定回归数学三 1987 十一(2)中，原卷 PDF 第 5 页的密度只含 a²，未给 a>0；答案册 PDF 第 9 页结果省略绝对值。独立执行者与主 Agent 视觉核验后确认，题干只要求 a≠0，通用期望结果应含 |a|。

原因 → 答案册的正态积分套式隐含把尺度参数 a 当成正数，若照抄会漏掉负参数情形。

防止规则 → 根据题干与密度有效性确定参数域；遇平方参数后开方时保留绝对值，并用正负参数交叉核验。答案册缺少条件时在当前测试报告记明，不修改源 PDF，也不把历史通过记录当成当前真值。

### 2026-09-11 · 旧索引标签与历史通过记录不能替代原题核验

现象 → 本轮发现数学一 2005 题1实际为斜渐近线，数学二 2005 题11为偏导而非线代，数学三 2005 题22应在PDF第72页，旧第75页属于2006年。修正标签后数学二仅2道线代，原“覆盖通过”不成立。

原因 → 旧索引的年份、题号、题型和页码没有逐项一致；机械统计标签与阅读旧报告掩盖真实覆盖缺口。

防止规则 → 固定题恢复时以原卷题号和年份双重确认身份；定位冲突后不把做对另一题计入原ID，意外看过答案则交给未见答案的执行者补测。修正分类后重新计算覆盖，保留已有固定题并补足缺失类别；历史报告用有日期的勘误纠正，不覆盖原执行记录。

### 2026-09-12 · 完成消息不能代替可恢复的结果摘要

现象 → 恢复时最后一道补测已有通过消息，但仅附临时报告路径，文件已不可读，归档缺少短结果。

原因 → 未及时将可公开摘要转入仓库，把临时路径当成可持久恢复证据。

防止规则 → 子 Agent 回传短结果、验证结论与定位，维护者逐步归档；完整真题仍不入库。恢复时只补核缺失部分，不凭通过消息编造细节或重复全部已存验证。

### 2026-09-12 · 中文内联脚本再次出现编码拒绝

现象 → 多文件中文内联 Python 在解析阶段再次报非 UTF-8 错误，未执行写入。

原因 → 该命令传输路径无法可靠保存本次长中文脚本；具体字节损坏来源未确认。

防止规则 → 中文文档内容直接使用单文件补丁；内联脚本只处理 ASCII 逻辑或读取现有 UTF-8 文件。失败后逐目标核对，不反复走已失败的传输路径。
